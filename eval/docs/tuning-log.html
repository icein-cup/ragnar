Model Size Comparison

Four model configurations were evaluated on an identical set of 20 in‑corpus questions and 10 out‑of‑corpus probes, replayed over identical retrieved contexts (single generation call per case; retrieval not repeated). Coverage is defined as the proportion of correct answers over all answerable questions. Probe refusal is the proportion of out‑of‑corpus questions correctly declined.

Increasing parameter count from 7B to 14B produced no measurable change in coverage (0.60 for both) or probe refusal (0.90 for both), at 1.7× the latency and 1.4× the resident memory. The 27B model, evaluated in its native thinking mode, gained 10 coverage points over the 7B baseline but required 32 GB resident memory and approximately 20 seconds per call before any agentic overhead — exceeding the latency budget independent of pipeline cost. qwen2.5:7b was retained as the production model. The prompt-wording change in Section 02 produced a larger coverage gain than doubling parameter count.

02

Refusal Sentinel Instruction

Evaluated whether instructing the model to prefix a genuine non-answer with a literal token (NO_ANSWER) improves refusal-detection reliability independent of a given model's phrasing habits. n=40 in-corpus, n=20 probes, qwen2.5:7b.

Coverage and refusal rate by instruction wording

refusal rate
Adopted

A sentinel instruction that also required the model to justify a refusal (v1) reduced coverage by 10 points relative to no sentinel, trading 4 correct answers for 2 correct refusals. A sentinel instruction stating an explicit answer-preference bias (v2) recovered the loss and additionally improved refusal rate by 10 points over the no-sentinel condition.

The answer-preference instruction is necessary to the sentinel's function on this model, not incidental to it.

answer_coverage — the primary outcome measure, which does not exclude refused cases from its denominator — increased by 3.3 points, within the scorer's documented uncertainty band of 2–5 points and not distinguishable from no effect. answer_accuracy (proportion correct among non-refused cases) decreased by 17.8 points. 05
Methodological finding

Evaluation sample size and composition determine whether a pipeline-level regression is detectable.

Two independent evaluation tiers each produced a false negative for a regression that the complete benchmark subsequently confirmed — each one tier more computationally expensive to run than the last.

Tier 1
Single-call replay
One generation call per case, over a fixed, previously-retrieved context (n=40–60, minutes to run). Does not exercise the self-correction stage and cannot measure a prompt's effect on refusal calibration under retrieval variance.
Regression not detected (Trial 1)
Tier 2
Full pipeline, partial sample
Complete retrieval, self-correction, and generation stages, evaluated on a subsample matched in size class to the replay (n=55, ~20 min). An unrepresentative subsample can depress both conditions equally and mask a regression concentrated outside the sampled cases.
Regression not detected (Trial 2)
Tier 3
Full 125-case benchmark
The only evaluation tier at which both regressions were detected (30–50 min per run). Required for any candidate expected to alter refusal frequency.
Regression detected, both trials

top_k and candidates control the number of chunks passed to the reranker and, subsequently, to the generation call. Unlike the two prompt trials above, this parameter does not alter refusal-instruction wording. Evaluated in two stages prior to full-benchmark confirmation.

Answer recall increased monotonically with top_k (0.75 at k=5, 0.80 at k=10); no case present in a lower-k result set was absent from a higher-k result set. At the generation stage, correct-answer count increased by 9 points with no increase in wrong-answer count; probe refusal decreased by 8.5 points (3 of 35 additional probes answered rather than declined).

The full 125-case agentic evaluation was subsequently completed across six configurations (Section 09). The 9-point gain did not reproduce. Both measurements above are retrieval-side: recall establishes that a document can be retrieved, and the single-call generation stage omits the multi-query, multi-hop, and self-correction stages through which retrieved context actually reaches the answer. Neither predicts pipeline coverage — the same class of false positive documented in Section 05, one tier earlier.

The agentic pipeline previously executed within a single blocking UI element with no intermediate output. Specified target: p50 ≤ 6–8s, p90 ≤ 15–20s. Measured p90 (53.5s) exceeds this target independent of any accuracy-affecting change. An accuracy improvement that further increases p90 does not constitute a net improvement under this constraint.

The target was subsequently restated as a hard ceiling — max ≤ 35s on every case, not a percentile — and the cross-encoder reranker was moved from the container (CPU) to the host GPU, where a 30-candidate rerank costs 1.48s rather than 10.34s. Worst single case fell from 144.9s to 26.5s, and p90 from 53.5s to 18.0s. Across the six sweep runs in Section 09 — 750 cases — no case exceeded the 35s ceiling, worst case 31.3s. answer_coverage spans 0.289–0.367 across all six configurations — a 7.8-point range against a 10-point tie threshold, on parameters that vary retrieval work by a factor of two. top_k at fixed candidates is not even monotonic (0.367 / 0.322 / 0.344 at k=5 / 8 / 10), so the incumbent k=10 was retained. candidates declines monotonically above 20 (0.367 / 0.344 / 0.344 / 0.289 at 20 / 25 / 30 / 40).

The ceiling is the decision to decline, and no retrieval-side parameter reaches it.

Selected — candidates=20, top_k=10

Selected on latency, where the differences are outside sampling variation: 2.6s per case faster at the mean than candidates=40 and 5.3s faster at p90, while tying the best coverage measured and posting the highest answer_accuracy of the six. candidates=40 is rejected on every axis — worst coverage, worst refusal accuracy, worst citation precision, slowest.

The coverage column should be read as six tied results, not a ranking — the tie threshold is sampling error over which 90 questions the golden set holds. It is not run-to-run noise: Section 13 re-ran one of these configurations two days later and reproduced all 90 case outcomes exactly.

Temperature 0.2 refused four more of the same cases than temperature 0.0 (44 vs. 40) and produced two fewer correct answers. answer_accuracy rose (0.737 → 0.765) only because refusals shrank its denominator — the precise artefact answer_coverage exists to expose. The hypothesis is not supported: sampling did not release the locked-in refusals.

The cost is unambiguous. Mean latency rose 9.26s → 11.72s, p90 18.26s → 21.09s, and the worst case 26.45s → 48.86s. Three cases breached the 35s ceiling where the six runs of Section 09 produced none in 750. A ceiling that binds on every case cannot be traded against a distribution improvement, and there was no improvement to trade.

Mechanism, from the case records: sampling lengthens generation before it stops. Each breaching case carries budget_exhausted — it overran the 25s in-pipeline expansion budget, and generation after that carried it past the ceiling. One case ran 39.4s at temperature 0.2 against 21.0s at 0.0 while doing less work (7 generated queries and 0 hops, against 10 and 3). The pinned seed fixes sampling; it does not fix decode length.

Not evaluated

Temperature 0.5 was planned conditional on 0.2 improving coverage; it was dropped without running, as it amplifies the mechanism producing the latency cost. query_temperature — which governs query rewriting and fan-out rather than answer decoding — was also deferred: with context_recall already at 0.889, query diversity competes for the ~11% of cases where evidence is genuinely missing, while roughly half of all answerable cases are declined with the evidence present.

Coverage is the documented primary metric, so mq=2 is selected — but if citation quality on bridge questions ever becomes the target, mq=3 is the defensible other side.

13
Methodological finding

The benchmark is deterministic end to end, which retires the caveat attached to every result above it.

The 3, 3 cell of Section 12 re-runs the exact configuration already measured in Section 09, two days later, on a different Docker daemon instance after a full restart. The two runs agree on all 90 in-corpus cases — zero flips: 45 refused, 33 correct, 12 wrong in both. At temperature 0 with models.seed pinned, this pipeline reproduces itself exactly.

Until this run, every table in this document carried a note that its differences might be re-run noise, because repeat-run variance had never been measured here. That note was wrong in its implication and is now removed. The 10-point tie threshold is binomial sampling error over n=90 — it answers “would a different set of 90 questions rank these differently”, which remains the right question for generalisation. It was never a statement about re-running the same configuration.

The honest reading of every sweep above is therefore: the differences are small, but real and reproducible — not noise. What a tie threshold still forbids is claiming that a 3-point win on these 90 questions would survive a different 90.

Retrieval Floor Calibration — score_floor × vector_floor

The two thresholds a retrieved chunk must clear to reach the model. They are OR'd — a chunk is kept if either its reranker score clears score_floor or its raw cosine similarity clears vector_floor. Both production values were flagged in config.yaml as not validly calibrated: the sweep that produced them left vector_floor at 0.0, so every candidate cleared the gate at every swept value and the sweep could not have discriminated. This phase re-derives them against the pipeline Sections 09 and 12 settled.

The premise of a floor does not hold on this corpus

Probes do not score lower than answerable questions. On cosine similarity they score higher — median 0.642 against 0.558. This is structural rather than a calibration failure: a HybridQA probe such as “What is the average annual rainfall in Multan?” retrieves the correct and genuinely relevant Multan table. The corpus is about the entity; it simply lacks the fact asked for. No retrieval-score threshold can see that distinction. Only a model reading the content can.

A 30-cell replay over a fresh uncensored run (20260828-200425, both floors at 0.0) identified 0.55/0.48 as the challenger. Replaying is arithmetic over saved scores rather than a re-run: seconds instead of 37 minutes per cell. Its winner was then confirmed live, which is what the runbook requires before config.yaml changes.

No change adopted — both floors held

The replay predicted 2 points of refusal_accuracy at zero coverage cost. Live, the higher floor lost 0.8 points of refusal accuracy, lost 1.1 points of coverage, and refused one probe fewer. Every gap sits inside the tie threshold, so the incumbent's rule applies and both values stand.

Their status has nonetheless changed. score_floor: 0.55 and vector_floor: 0.42 now rest on a sweep against the settled pipeline plus a live confirmation, rather than on the broken calibration the code comments describe. The NOT VALIDLY CALIBRATED warning should now be read as confirmed adequate, effect size approximately one case.

Why the replay mispredicted — open defect

replay_floor.py's apply_floor sets refused = not kept, overwriting whatever the model itself decided with what the floor decides. In the uncensored run, 76 of 125 cases were model refusals — so the replay ranked cells on a quantity the live pipeline never computes, and reported coverage 0.433 against the run's actual 0.367.

The script already documented this bias as an upper/lower bound. What the confirm run adds is that the bias is not uniform across cells, so cell-to-cell ranking does not survive it. The tool's usable output is its wiped-case counts and score distributions, not its metric columns. Fix is one line; not yet applied.

Recorded for a different objective

The one substantial effect in the phase is on citations: citation_precision rose 0.419 → 0.477 at vector_floor=0.48, the largest single-metric move measured, because a stricter vector floor prunes marginal chunks that were being cited. It costs about one point of coverage. If citation quality ever displaces coverage as the target, that is the lever.

The quality ceiling was never in this table

Phase 4 is the only phase that reduces the tail's cause

Five chunks of 2846 (0.2%) exceed 4000 characters, the largest at 10409, and all five are tables. A query that retrieves one pays roughly 5× on every rerank in its fan-out — 1.74s becomes 9.00s, measured. Prose is already bounded; 258 chunks sit at exactly 1750 characters and only tables exceed it.

Halving the rows per table group would shrink four of the five. It cannot bound them: the fifth reaches 9804 characters from only 9 rows of long cell content, and the parameter counts rows rather than characters. Report worst-case latency on every row of this phase — before this effect was identified, any chunking comparison measured quality while silently varying latency.
